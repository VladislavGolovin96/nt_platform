# Финальный отчёт о разработке

**NT Platform — платформа нагрузочного тестирования**

---

## 1. Что было сделано

NT Platform — рабочая веб-платформа для запуска нагрузочного тестирования через браузер. Пользователь указывает Git-репозиторий с Gatling-сценариями, платформа его собирает, запускает тест и формирует PDF-отчёт с реальными метриками.

Реализованы шесть микросервисов, React SPA, полная инфраструктура в docker-compose и event-driven коммуникация через Kafka. Всё поднимается одной командой.

### Что работает end-to-end

1. Регистрация → вход → JWT + refresh token + blacklist в Redis
2. Создание проекта из Git → клонирование → сборка Maven/Gradle → обнаружение Simulation-классов → хранение артефактов в MinIO
3. Запуск теста → Gatling запускается как внешний процесс → логи стримятся через Kafka → SSE в браузер → результаты в MongoDB
4. Генерация PDF-отчёта: парсинг `simulation.log`, расчёт p50/p75/p95/p99, breakdown по эндпоинтам, вердикт PASS/FAIL, загрузка в MinIO
5. Скачивание PDF через presigned URL
6. Уведомления о завершении теста (email через Mailhog, webhook)


---

## 2. Архитектура

Платформа построена по принципу event-driven microservices. Сервисы не вызывают друг друга напрямую — они публикуют события в Kafka и реагируют на чужие.

Единственное исключение: API Gateway синхронно проверяет JWT через Auth Service (`GET /api/auth/validate`) на каждый входящий запрос. Это осознанный компромис: downstream-сервисы освобождены от логики аутентификации.

### Микросервисы

| Сервис | Порт | Ответственность |
|--------|------|-----------------|
| API Gateway | 8080 | Маршрутизация, JWT-валидация, Rate Limiting, LB |
| Auth Service | 8081 | Регистрация, вход, refresh token, logout |
| Project Service | 8082 | Git clone, сборка проекта, хранение артефактов |
| Execution Service | 8083 | Запуск Gatling, стриминг логов, управление статусом |
| Report Service | 8084 | Генерация PDF из simulation.log |
| Notification Service | 8085 | Email и webhook-уведомления |

## 3. Обоснование технических решений

### 3.1. Java 21 + Spring Boot 3.3.x

Java 21 — LTS-версия с Virtual Threads (Project Loom). На практике в этом проекте стриминг SSE и Kafka-листенеры выигрывают от неблокирующей модели. Spring Boot 3.3.x — актуальная версия с нативной поддержкой Java 21, Spring Security 6, Spring Cloud Gateway 4.

Обоснование: я хоть что-то понимаю в этом стеке *meme*

### 3.2. Spring Cloud Gateway

Gateway занимается тремя вещами: маршрутизацией, JWT-валидацией и rate limiting. Это осознанный выбор в сторону централизации, поскольку downstream-сервисы не знают ничего об аутентификации, не тащат Spring Security, не дублируют код, что есть +вайб

Bucket4j + Spring Data Redis реализует token bucket алгоритм: 100 req/min на пользователя (по sub из JWT), 10 req/min на POST /executions. Счётчики хранятся в Redis — это работает корректно даже если Gateway масштабируется горизонтально.

Round Robin балансировка через Spring Cloud LoadBalancer. В docker-compose она не нужна (один инстанс каждого сервиса), но код готов к горизонтальному масштабированию без изменений.

### 3.3. Apache Kafka vs RabbitMQ vs NATS

Это самый неоднозначный выбор в проекте.

**Kafka** — log-based брокер. Сообщения хранятся на диске и не удаляются после потребления. Несколько consumer group могут читать один и тот же топик независимо. Именно поэтому `test.finished` одновременно обрабатывают Report Service и Notification Service без какой-либо координации между ними. Если Report Service упал и пропустил сообщение, он может прочитать его снова с нужного offset.

**RabbitMQ** — классическая очередь сообщений. Сообщение удаляется после подтверждения. Для fan-out (одно событие — несколько консьюмеров) нужно создавать exchange с привязками, что добавляет конфигурации. Зато RabbitMQ проще в операционном плане, потребляет меньше ресурсов и имеет меньшую задержку.

**NATS JetStream** — наиболее лёгкий вариант с персистентностью. Очень низкая задержка, простой протокол, минимальный overhead. JetStream появился относительно недавно, экосистема меньше, чем у Kafka или RabbitMQ.

**Выбор Kafka обоснован:**
- Персистентность событий — можно перечитать `test.finished` после рестарта сервиса
- Consumer groups с независимым offset для каждой — Report Service и Notification Service читают топик независимо
- Хорошо документированная интеграция со Spring (spring-kafka)
- EDA-паттерн реализуется без дополнительной конфигурации: новый consumer просто подписывается на топик

**Честная оценка:** для текущего масштаба проекта Kafka избыточна. Нагрузка — несколько событий при каждом запуске теста, запуски происходят десятки раз в день максимум. При таком объёме RabbitMQ был бы проще в настройке и потреблял бы меньше RAM. с NATS было бы еще проще.

Kafka оправдана, если платформа вырастет до десятков параллельных тестов с детальным логированием (топик `test.log.{executionId}` может генерировать тысячи сообщений за один тест). В этом случае высокая пропускная способность Kafka становится реальным преимуществом.

Но главное преимущество это то, что я поработал с ней ручками на уровне создания. Мне кажется это весомый аргумент
### 3.4. Event-Driven Architecture (EDA)

Платформа построена по принципу EDA: сервисы реагируют на события, не зная ничего друг о друге.

Пример: Execution Service публикует `test.finished` и на этом заканчивает своё участие. Что произойдёт дальше — не его забота. Report Service и Notification Service подписываются независимо. Чтобы добавить новый сервис (например, сохранение метрик в отдельную аналитическую БД), достаточно написать ещё одного консьюмера — Execution Service не нужно трогать.

Это снизило связность между сервисами и упростило тестирование каждого из них.

Обратная сторона: отладка сложнее. Если что-то сломалось, нужно смотреть логи нескольких сервисов и состояние Kafka — нет одного места, где виден весь путь запроса. Для такого масштаба это приемлемый компромисс.

### 3.5. PostgreSQL

PostgreSQL хранит транзакционные данные: пользователи, проекты, запуски, отчёты, refresh-токены, webhook-подписки. Всё, что требует ACID-гарантий.

Миграции — Flyway. Версионированные SQL-файлы запускаются при старте каждого сервиса. Это гарантирует согласованность схемы между окружениями и не требует ручного применения SQL.

Можно было использовать MongoDB везде, но транзакционные требования у auth-данных и истории запусков делают реляционную БД более подходящим выбором.

### 3.6. MongoDB

MongoDB хранит логи выполнения Gatling: одна коллекция `execution_logs`, document для каждой строки stdout/stderr. За время одного теста накапливаются тысячи строк.

Почему не PostgreSQL для логов: документная модель лучше подходит для append-only логов без фиксированной схемы. MongoDB не требует миграций при изменении формата строки лога. Горизонтальное шардирование по `executionId` — естественный следующий шаг при росте.

Почему не Elasticsearch: оверинжиниринг для данного проекта. Полнотекстовый поиск по логам не требовался.

### 3.7. Redis / Valkey

Redis выполняет три функции:

1. **JWT blacklist** — SET с TTL, равным оставшемуся времени жизни токена. При logout токен попадает в blacklist; Gateway проверяет его при каждом запросе.
2. **Rate Limiting** — Bucket4j хранит счётчики в Redis. При нескольких инстансах Gateway счётчики общие.
3. **Статус выполнения** — ключ `execution:status:{id}` с TTL 24 часа. Быстрый доступ к текущему статусу без запроса к PostgreSQL.


### 3.8. MinIO

MinIO хранит два типа файлов:
- **artifacts** — скомпилированные test-classes проекта (`{userId}/{projectId}/test-classes-{ts}.tar.gz`)
- **reports** — готовые PDF-отчёты

Файлы не отдаются через Java-сервис. Вместо этого генерируется presigned URL — ссылка с HMAC-подписью, по которой браузер скачивает файл напрямую из MinIO. Это разгружает сервис от роли файлового прокси.

Тонкий момент: presigned URL включает hostname в подпись. В Docker-сети сервисы обращаются к MinIO по имени `minio:9000`, но браузер не видит это имя. Решение — два S3-клиента: один для внутренних операций (upload, exist-check), второй настроен на `localhost:9000` и используется только для генерации presigned URL.

### 3.9. Gatling 3.10.5

Gatling запускается как внешний процесс через ProcessBuilder, не как зависимость JVM. Это намеренное ограничение: Gatling использует Akka под капотом, его classpath конфликтует с Spring Boot. Запуск через `java -cp` с отдельным classpath изолирует процессы.

Результаты записываются в `/tmp/gatling-results/{executionId}` — Docker volume, смонтированный одновременно в Execution Service и Report Service. Так Report Service читает `simulation.log` напрямую, без передачи файла через сеть.

### 3.10. iText 7

PDF генерируется через iText 7 (AGPL лицензия). Отчёт содержит:
- Метаданные запуска (тип теста, длительность, цель)
- KPI-карточки (суммарные запросы, error rate, throughput)
- Таблицу перцентилей (min / mean / p50 / p75 / p95 / p99 / max)
- Breakdown по эндпоинтам с вердиктом PASS/FAIL на строку
- Распределение по бакетам (<800ms, 800–1200ms, ≥1200ms)
- Итоговый вердикт с конкретными значениями vs пороги
Но стоит признаться, что отчет не самый лучший получился, просто я уже был на грани срыва.

Метрики берутся из `simulation.log` через `GatlingLogParser` —  формат с записями RUN/REQUEST/USER.

### 3.11. React + Vite + React Query

На уровне фронта сильно замарачиваться не стал. Сделал SPA на базе React Query. Его преимущество в том, что он обслуживает кэширование и polling (статус выполнения обновляется каждые 3 секунды, пока тест не завершён). SSE-соединение для логов реализовано через нативный `fetch` с `ReadableStream` — это позволяет добавить Authorization header, который `EventSource` не поддерживает.

## 5. Слой роутинга

### Маршрутизация

API Gateway принимает все внешние запросы и маршрутизирует их по префиксу пути:

```
/api/auth/**          → auth-service:8081
/api/projects/**      → project-service:8082
/api/executions/**    → execution-service:8083
/api/reports/**       → report-service:8084
/api/notifications/** → notification-service:8085
```

SSE-поток (`/api/executions/{id}/logs`) проксируется как есть: Gateway не буферизует Server-Sent Events. Можно конечно было реализовать через websocket, но как говорится: Можно, а зачем?

### Балансировка

Spring Cloud LoadBalancer применяет Round Robin между инстансами каждого сервиса. В docker-compose каждого сервиса один инстанс, но при горизонтальном масштабировании изменений в коде не потребуется.

### Rate Limiting

Bucket4j + Redis реализует token bucket:
- Глобально: 100 запросов в минуту на пользователя (ключ — `sub` из JWT)
- На POST /executions: 10 запросов в минуту (защита от параллельного запуска большого числа тестов)

При превышении лимита — HTTP 429 Too Many Requests.

## 6. Проблемы, с которыми столкнулись

**Kafka deserialization при отсутствии type headers.** Execution Service публикует события без Kafka type headers (`spring.json.add.type.headers: false`). Report Service не знал, в какой класс десериализовать payload, и падал с исключением. Решение: `spring.json.value.default.type` в конфигурации consumer. Notification Service слушает несколько типов событий, поэтому там использован `StringDeserializer` с ручным парсингом через ObjectMapper.

**100% CPU из-за Kafka poison pill.** SerializationException в consumer не обрабатывалась DefaultErrorHandler, consumer перезапускался мгновенно в бесконечном цикле. Решение: `DefaultErrorHandler` с `ExponentialBackOff` (старт 1с, максимум 30с) и явным добавлением `SerializationException` в список не-ретрабельных исключений.
+ я забыл добавить лимит на запись логов отчего мой Docker.raw мгновенно съедал память. Изначально я был уверен, что лимит на запись есть. У меня ушло 1.5 часа на локализацию. -1.5 из моей жизни в пустую из-за невнимательности...

**Presigned URL с внутренним hostname.** MinIO генерировал presigned URL с hostname `minio:9000`. Браузер не мог этот адрес разрешить. Первая попытка — замена hostname строкой в Java — давала HTTP 403, потому что AWS HMAC-подпись включает hostname. Решение: два S3-клиента — один для операций с internal endpoint, второй настроен на `localhost:9000` и используется только для генерации URL.

**Spring self-invocation и @Transactional.** `@Async` метод `generateReport()` вызывал `this.markFailed()` — Spring AOP proxy обходился, `@Transactional` не применялась, Hibernate бросал `TransactionRequiredException`. Решение: `@Transactional` перенесена непосредственно на `@Modifying`-методы репозитория, где она применяется независимо от того, кто вызывает метод.

**simulation.log недоступен для Report Service.** Gatling пишет результаты в контейнер Execution Service. Report Service в другом контейнере. Решение: named Docker volume `gatling-results`, смонтированный в оба контейнера по одному и тому же пути.
