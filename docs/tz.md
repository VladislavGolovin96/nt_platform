# Техническое задание

**NT Platform — платформа автоматизированного нагрузочного тестирования**

ГОСТ 34.602-89, ГОСТ 19.201-78 (ключевые разделы)

---

## 1. Общие сведения

**Полное наименование:** Веб-платформа автоматизированного нагрузочного тестирования NT Platform.

**Условное обозначение:** NT Platform.

**Основание для разработки:** учебный проект в рамках курса «Программная инженерия».

**Разработчик:** команда учебного проекта.

**Плановые сроки:** определяются учебным планом семестра.

---

## 2. Назначение и цели системы

### 2.1. Назначение

NT Platform — сервис для запуска, мониторинга и анализа результатов нагрузочного тестирования HTTP-приложений на базе Gatling (Java DSL). Пользователь указывает Git-репозиторий с готовыми сценариями Gatling, выбирает тип теста и получает PDF-отчёт с перцентилями задержки, пропускной способностью и вердиктом PASS/FAIL.

Платформа устраняет необходимость устанавливать Gatling локально: среда выполнения инкапсулирована в Docker-контейнер.

### 2.2. Цели создания

1. Автоматизировать цикл «добавить репозиторий → собрать → запустить тест → получить отчёт» через веб-интерфейс.
2. Обеспечить наблюдаемость в реальном времени: стриминг логов Gatling через SSE.
3. Формировать структурированный PDF-отчёт на основе данных из `simulation.log`.
4. Уведомлять пользователя о завершении теста через webhook или email.

---

## 3. Характеристика объекта автоматизации

Целевая аудитория — разработчики и QA-инженеры, которые уже написали Gatling-сценарии и хотят запускать их против staging или production-окружения, не настраивая локальную среду. Типичная частота запусков — от нескольких раз в день до нескольких раз в неделю на один проект.

Платформа не предназначена для тестирования с десятками тысяч параллельных пользователей: в текущей реализации Gatling запускается как единый процесс на одном узле.

## 4. Требования к системе

### 4.1. Требования к системе в целом

| Код | Требование |
|-----|------------|
| R-01 | Система запускается одной командой `docker compose up -d` без ручной настройки каждого сервиса. |
| R-02 | Отказ отдельного сервиса не приводит к полной неработоспособности платформы. |
| R-03 | Взаимодействие между сервисами — асинхронное через Kafka. Синхронный HTTP — только для валидации JWT в Gateway. |
| R-04 | Сервисы stateless: состояние хранится в PostgreSQL, MongoDB, Redis. |
| R-05 | При перезапуске любого сервиса данные не теряются. |
| R-06 | Каждый запрос к API проходит JWT-валидацию на уровне API Gateway. |
| R-07 | Rate limiting: не более 100 запросов в минуту на пользователя, не более 10 на POST /executions. |

### 4.2. Требования к функциям

| Код | Функция | Приоритет |
|-----|---------|-----------|
| F-01 | Регистрация и вход (JWT + refresh token, blacklist в Redis) | Обязательно |
| F-02 | Добавление Git-репозитория с Gatling-сценариями (clone через JGit) | Обязательно |
| F-03 | Сборка проекта (Maven/Gradle) и обнаружение классов Simulation | Обязательно |
| F-04 | Запуск теста с выбором типа: SMOKE, LOAD, STRESS, SPIKE, RELIABILITY | Обязательно |
| F-05 | Стриминг логов в реальном времени через Server-Sent Events | Обязательно |
| F-06 | Остановка выполняющегося теста | Обязательно |
| F-07 | Генерация PDF-отчёта из `simulation.log` (перцентили, breakdown по эндпоинтам, PASS/FAIL) | Обязательно |
| F-08 | Скачивание PDF через presigned URL (MinIO) | Обязательно |
| F-09 | История запусков с метаданными (тип, статус, длительность) | Обязательно |
| F-10 | Уведомления о завершении теста (webhook, email) | Желательно |
| F-11 | Управление webhook-подписками | Желательно |

### 4.3. Требования к видам обеспечения

**Программное обеспечение**

| Компонент | Технология |
|-----------|------------|
| Backend-сервисы | Java 21, Spring Boot 3.3.x |
| API Gateway | Spring Cloud Gateway 4.x |
| Брокер сообщений | Apache Kafka 7.6.0 (KRaft, без ZooKeeper) |
| Реляционная БД | PostgreSQL 16 |
| Документная БД | MongoDB 7 |
| Кэш | Redis/Valkey 7 |
| Объектное хранилище | MinIO (S3-совместимое) |
| Движок тестирования | Gatling 3.10.5 |
| PDF-генерация | iText 7 |
| Frontend | React 18, Vite 5, React Query v5 |

**Аппаратное обеспечение (минимальные требования для локального запуска)**

- CPU: 4 ядра
- RAM: 8 ГБ (рекомендуется 16 ГБ)
- Диск: 10 ГБ свободного места

**Требования к безопасности**

- Все запросы валидируются по JWT на уровне Gateway; downstream-сервисы JWT не проверяют.
- Файлы в MinIO недоступны публично; скачивание происходит через presigned URL с ограниченным временем жизни.
- JWT secret — не менее 256 бит.
- Пароли хранятся в виде BCrypt-хэша.

## 6. Порядок контроля и приёмки

Система считается принятой при выполнении следующих условий:

1. Пользователь регистрируется, создаёт проект из публичного Git-репозитория, собирает его и запускает тест через веб-интерфейс.
2. Во время теста в браузере отображается стриминг логов Gatling.
3. После завершения теста генерируется PDF-отчёт с реальными перцентилями задержки.
4. PDF доступен для скачивания через кнопку в интерфейсе.
5. Все 17 контейнеров запускаются командой `docker compose up -d` без ошибок.
