# Пользовательские истории, варианты использования и нефункциональные требования

**NT Platform**

---

## 1. Роли пользователей

**User** — разработчик или QA-инженер. Работает с платформой через браузер: добавляет проекты, запускает тесты, смотрит результаты. Других ролей в текущей версии нет: у каждого пользователя собственный изолированный набор проектов и отчётов.

---

## 2. User Stories

### Аутентификация

**US-01.** Я хочу зарегистрироваться по email и паролю, чтобы получить доступ к платформе.

*Критерии приёмки:*
- Форма принимает username, email, пароль.
- Пароль короче 8 символов — ошибка валидации.
- После успешной регистрации выполняется автоматический вход.
- Дублирующийся email или username — понятное сообщение об ошибке.

**US-02.** Я хочу входить в систему и оставаться авторизованным, пока сам не выйду.

*Критерии приёмки:*
- Вход по username + пароль, выдаётся пара access/refresh токенов.
- Access token живёт 15 минут; при истечении клиент автоматически обновляет его через refresh token.
- Refresh token живёт 7 дней.
- После нажатия «Выйти» access token попадает в blacklist в Redis; повторное использование невозможно.

---

### Управление проектами

**US-03.** Я хочу добавить Git-репозиторий с Gatling-сценариями, чтобы платформа могла их собрать и запускать.

*Критерии приёмки:*
- Форма принимает: название, URL репозитория, ветку, инструмент сборки (Maven/Gradle).
- После создания проект отображается в списке со статусом PENDING → CLONING → BUILDING → READY.
- Если репозиторий недоступен или сборка упала, статус становится FAILED с сообщением об ошибке.

**US-04.** Я хочу видеть список Simulation-классов в проекте, чтобы выбрать нужный перед запуском теста.

*Критерии приёмки:*
- После успешной сборки платформа находит все классы, наследующие `Simulation`, и показывает их список.
- Без успешной сборки запуск теста недоступен.

**US-05.** Я хочу пересинхронизировать проект (git pull + пересборка), если обновил сценарии в репозитории.

*Критерии приёмки:*
- Кнопка «Sync» доступна в любом статусе проекта.
- Процесс синхронизации показывает текущий статус.

---

### Запуск и мониторинг тестов

**US-06.** Я хочу запустить нагрузочный тест, выбрав класс симуляции и тип теста.

*Критерии приёмки:*
- Доступные типы: SMOKE, LOAD, STRESS, SPIKE, RELIABILITY.
- После запуска создаётся запись выполнения со статусом PENDING → RUNNING.
- Если Gatling не может запуститься, статус переходит в FAILED.

**US-07.** Я хочу видеть логи Gatling в реальном времени прямо в браузере.

*Критерии приёмки:*
- Логи появляются в виде терминала с прокруткой.
- Соединение — SSE; при разрыве браузер переподключается автоматически.
- История логов доступна после завершения теста.


---

### Отчёты

**US-08.** Я хочу получить PDF-отчёт после завершения теста.

*Критерии приёмки:*
- Отчёт генерируется автоматически после получения события `test.finished`.
- Отчёт содержит: перцентили задержки (p50/p75/p95/p99), пропускную способность, breakdown по эндпоинтам, вердикт PASS/FAIL.
- Статус отчёта виден на странице выполнения: GENERATING → READY.

**US-09.** Я хочу скачать PDF-отчёт одной кнопкой.

*Критерии приёмки:*
- Кнопка «Download PDF» появляется при статусе READY.
- Файл скачивается через presigned URL; токен в URL действует ограниченное время.
- Сам PDF-файл не стримится через Java-сервис.

---

### Уведомления

**US-11.** Я хочу получать уведомления о завершении теста, чтобы не ждать результат в браузере.

*Критерии приёмки:*
- Доступные каналы: email и webhook.
- При завершении теста (SUCCESS или FAILED) уходит уведомление с executionId, статусом и длительностью.
- При генерации отчёта уходит отдельное уведомление со ссылкой на скачивание.

**US-12.** Я хочу зарегистрировать webhook, чтобы платформа отправляла события в мою систему.

*Критерии приёмки:*
- POST /api/notifications/webhooks с URL и списком событий.
- Webhook вызывается при каждом совпадающем событии.
- История вызовов доступна через GET /api/notifications/history.

## 3. Варианты использования (Use Cases)

### UC-01: Регистрация

**Актор:** незарегистрированный пользователь  
**Предусловие:** пользователь открыл `/register`  
**Основной поток:**
1. Пользователь вводит username, email, пароль и подтверждение пароля.
2. Клиент отправляет POST /api/auth/register.
3. Auth Service валидирует данные, хэширует пароль (BCrypt), создаёт запись в `users`.
4. Возвращается пара токенов; клиент сохраняет их в localStorage и перенаправляет на `/projects`.

**Альтернативный поток — дубликат:**
На шаге 3 обнаружено совпадение по email или username → HTTP 409, отображается ошибка.

---

### UC-02: Создание проекта

**Актор:** авторизованный пользователь  
**Предусловие:** пользователь на странице `/projects`  
**Основной поток:**
1. Пользователь нажимает «New Project», заполняет форму.
2. POST /api/projects → Project Service создаёт запись (статус PENDING).
3. Асинхронно: JGit клонирует репозиторий, Maven/Gradle собирает `test-classes`.
4. Project Service обнаруживает Simulation-классы, упаковывает артефакты, загружает в MinIO.
5. Статус → PROJECT_READY; публикуется событие `project.built` в Kafka.
6. Пользователь видит статус READY и список симуляций.

**Альтернативный поток — недоступный репозиторий:**
На шаге 3 JGit не может выполнить clone → статус FAILED, сообщение об ошибке сохраняется в БД.

---

### UC-03: Запуск теста

**Актор:** авторизованный пользователь  
**Предусловие:** проект в статусе READY  
**Основной поток:**
1. Пользователь выбирает класс симуляции и тип теста, нажимает «Start».
2. POST /api/executions → Execution Service создаёт запись (статус PENDING).
3. Execution Service скачивает артефакт из MinIO, запускает Gatling через ProcessBuilder.
4. Статус → RUNNING; публикуется `test.started`.
5. Stdout/stderr Gatling читаются построчно → каждая строка идёт в Kafka (`test.log.{executionId}`) и MongoDB.
6. Пользователь видит логи в реальном времени через SSE.
7. Gatling завершается → публикуется `test.finished`; статус → SUCCESS или FAILED.

**Альтернативный поток — ошибка запуска:**
ProcessBuilder не может запустить JVM → `test.failed` в Kafka, статус FAILED.

---

### UC-04: Генерация отчёта

**Актор:** система (автоматически, по событию)  
**Триггер:** событие `test.finished` в Kafka  
**Основной поток:**
1. Report Service получает событие.
2. Читает метаданные выполнения из PostgreSQL.
3. Парсит `simulation.log` из общего Docker volume (`gatling-results`).
4. Опционально запрашивает PNG-панели из Grafana Render API.
5. Генерирует PDF через iText 7.
6. Загружает PDF в MinIO (bucket `reports`).
7. Публикует `report.generated`; статус отчёта → READY.

---

### UC-05: Скачивание отчёта

**Актор:** авторизованный пользователь  
**Предусловие:** отчёт в статусе READY  
**Основной поток:**
1. GET /api/reports/{executionId}/download.
2. Report Service находит pdf_path в БД.
3. Генерирует presigned URL через MinIO SDK (public endpoint).
4. Клиент выполняет GET напрямую на MinIO, браузер скачивает файл.

## 4. Нефункциональные требования (NFR)

### Производительность

| # | Требование |
|---|------------|
| NFR-P-01 | API Gateway отвечает на запросы к auth/projects/executions не более чем за 500 мс при нормальной нагрузке. |
| NFR-P-02 | Генерация PDF-отчёта завершается не более чем за 30 секунд. |
| NFR-P-03 | SSE-соединение устанавливается не более чем за 2 секунды после начала выполнения теста. |

### Надёжность

| # | Требование |
|---|------------|
| NFR-R-01 | При недоступности Grafana отчёт генерируется без графиков; ошибка не прерывает процесс. |
| NFR-R-02 | Kafka-consumer использует ExponentialBackOff (начало 1 с, максимум 30 с) при временных сбоях. |
| NFR-R-03 | Flyway применяет миграции при старте сервиса; откат при несовместимом изменении схемы блокирует запуск. |

### Безопасность

| # | Требование |
|---|------------|
| NFR-S-01 | Каждый запрос к /api/** (кроме /api/auth/register и /api/auth/login) требует валидного JWT. |
| NFR-S-02 | Rate Limiter блокирует более 100 запросов в минуту от одного пользователя (по sub из JWT). |
| NFR-S-03 | Presigned URL для скачивания PDF действует ограниченное время; прямой доступ к bucket закрыт. |
| NFR-S-04 | JWT secret задаётся через переменную окружения и не хранится в коде или репозитории. |

### Наблюдаемость

| # | Требование |
|---|------------|
| NFR-O-01 | Каждый сервис публикует метрики в формате Prometheus через `/actuator/prometheus`. |
| NFR-O-02 | Grafana настроена с provisioning-дашбордами; не требует ручной настройки после запуска. |
| NFR-O-03 | Все сервисы логируют в JSON-формате в docker-профиле для совместимости с log-агрегаторами. |
| NFR-O-04 | Ротация логов Docker настроена: max-size 10 МБ, max-file 3. |

### Сопровождаемость

| # | Требование |
|---|------------|
| NFR-M-01 | Каждый сервис собирается и запускается независимо. |
| NFR-M-02 | Конфигурация передаётся только через переменные окружения; никаких hardcoded значений в коде. |
| NFR-M-03 | Схема PostgreSQL управляется Flyway-миграциями; изменения схемы версионируются. |

### Масштабируемость

| # | Требование |
|---|------------|
| NFR-SC-01 | Сервисы stateless: горизонтальное масштабирование возможно без изменения кода (кроме Execution Service, который запускает Gatling-процессы локально). |
| NFR-SC-02 | API Gateway балансирует нагрузку между несколькими инстансами downstream-сервисов по алгоритму Round Robin. |
